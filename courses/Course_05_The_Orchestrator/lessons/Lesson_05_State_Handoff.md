# State Handoff: JSON Outputs That Aggregate Without Re-reading

It is Wednesday at 08:45. You ran the full orchestrator yesterday afternoon. All five workers completed. The `batch-outputs/` folder now holds five JSON files and 50 scorecard markdown files. Your VP wants the portfolio summary by noon. You could tell the orchestrator to read all 50 scorecard files, but that would fill the context window with thousands of lines of individual commentary. The smarter move: read only the five batch-summary JSON files. They already contain every number the portfolio summary needs.

## The S2P problem

Atlas Procurement Services scores 50 suppliers every quarter. The individual scorecards are for category managers. The portfolio summary is for the VP and the board. Building that summary by re-reading 50 separate files is slow, error-prone, and wasteful. If each scorecard is 40 lines, that is 2,000 lines of text for the orchestrator to process, most of it commentary it does not need. The batch-summary JSON files hold the same scores in 50 compact records across five files. That is the data the orchestrator actually needs.

## What Claude Code does for you

The orchestrator reads five JSON files (one per category), merges the 50 supplier records into a single list, sorts by overall score, computes the portfolio average, and writes a structured portfolio summary to `outputs/`. No re-reading of individual scorecards. No context wasted on narrative text. The aggregation step takes seconds.

## Set up

1. You have completed Lesson 4. All five workers have run successfully.
2. The `batch-outputs/` folder contains: `batch-raw-materials.json`, `batch-logistics.json`, `batch-it-services.json`, `batch-facilities.json`, `batch-professional-services.json`.
3. The `batch-outputs/` folder also contains 50 `scorecard-*.md` files. You will not read these.
4. The `outputs/` folder exists in your practice directory.

## Step by step

### Step 1. Write the aggregation instruction

Tell the orchestrator to read only the five JSON files. Be explicit about what it should not read.

```
After all five workers complete, read these five files from batch-outputs/:
- batch-raw-materials.json
- batch-logistics.json
- batch-it-services.json
- batch-facilities.json
- batch-professional-services.json

Do NOT read the individual scorecard-*.md files. All data you need is in the five JSON files.
```

You should see a clear list of five file names and an explicit instruction to skip the 50 individual files.

### Step 2. Define the merge logic

Tell the orchestrator how to combine the five JSON files into one dataset.

```
From each JSON file, extract:
- category (string)
- category_average (number)
- suppliers (array of 10 objects)

Merge all 50 supplier objects into a single list. Compute the portfolio_average as the mean of all 50 overall_score values. Count suppliers by tier: strategic, preferred, approved. Count suppliers where risk_flag is true.
```

You should see four computed values: portfolio average, tier counts, and flagged count. These come from looping through the merged list, not from re-reading source data.

### Step 3. Define the portfolio summary structure

Specify the five sections the orchestrator writes to the final output file.

```
Save the portfolio summary to outputs/portfolio-summary-2026-Q1-2026-04-25.md with these sections:

## Section 1: Portfolio overview
One paragraph. State: 50 suppliers scored, the portfolio average score, count by tier, count flagged for risk.

## Section 2: Category averages
Table with columns: Category, Supplier Count, Average Score, Highest Scorer (name and score), Lowest Scorer (name and score).
Pull category_average from each JSON file's top level. Identify highest and lowest scorer from each file's suppliers array.

## Section 3: Top 10 suppliers by overall score
Sort all 50 suppliers by overall_score descending. Take the top 10.
Table with columns: Rank, Supplier, Category, Tier, Score, Trend.

## Section 4: Flagged suppliers
Filter all 50 suppliers where risk_flag is true.
Table with columns: Supplier, Category, Score, Flag Reasons, Recommended Action.
Each recommended action must name a specific deadline (within 14 days of 2026-04-25).

## Section 5: Trend analysis
Count suppliers by trend: improving, declining, stable. The three counts must sum to 50.
Name the three suppliers with the largest quarter-over-quarter score increase and the three with the largest decrease.

## Audit footer
"Generated by Claude Code on 2026-04-25. Data sources: supplier-master.csv, q1-performance.csv, scorecard-history.csv, risk-signals.csv. Scorecard weights: quality 25%, delivery 20%, responsiveness 15%, cost 25%, innovation 15%."
```

You should see five named sections plus an audit footer. Every section pulls data from the merged supplier list or from the top-level category fields. No section requires re-reading source CSV files.

### Step 4. Add a verification step

Tell the orchestrator to check its own math before saving.

```
Before saving the portfolio summary, verify:
1. You have exactly 50 suppliers in the merged list (10 per category).
2. The portfolio average equals the mean of all 50 overall_score values.
3. Each category average in Section 2 matches the category_average field from that batch's JSON file.
4. The trend counts in Section 5 sum to 50.
5. Every supplier in Section 4 (flagged) has risk_flag: true in the merged data.
```

You should see five self-check rules. If any check fails, the orchestrator should stop and report the mismatch before saving.

## Worked example: run the aggregation

After all five workers have completed, add the aggregation instructions to your orchestrator prompt and run it.

```
Read the five batch-summary JSON files from batch-outputs/. Merge all 50 suppliers. Compute portfolio average. Build the portfolio summary with the five sections described above. Verify the five checks. Save to outputs/portfolio-summary-2026-Q1-2026-04-25.md.
```

You should see a file appear in `outputs/` named `portfolio-summary-2026-Q1-2026-04-25.md`. Open it and verify:

1. The portfolio overview paragraph states 50 suppliers and a portfolio average score.
2. The category averages table has five rows, one per category.
3. The top 10 table is sorted by score descending.
4. The flagged suppliers table includes Apex Electronics (SUP004), Lakeshore Drayage (SUP019), and Ironside Recruiting (SUP048), each with specific flag reasons and deadlines.
5. The trend analysis counts sum to 50.
6. The audit footer lists all four data sources and all five weights.

## Common mistakes and how to recover

**Re-reading individual scorecard files.** If the orchestrator prompt says "read all scorecard files in batch-outputs/," it pulls 50 markdown files into context. That wastes tokens and risks hitting the context limit. Symptom: the orchestrator's response slows down or truncates the summary. Fix: name only the five JSON files in the read instruction.

**Inconsistent JSON keys between workers.** If one worker uses `overall_score` and another uses `weighted_score`, the merge fails silently. The orchestrator reads the wrong key and gets `null` or skips the supplier. Symptom: the merged list has fewer than 50 records, or some scores show as zero. Fix: go back to Lesson 4 and verify every worker prompt uses the identical JSON template with identical key names.

**Forgetting to verify totals.** Without the verification step, the orchestrator may produce a summary where the category averages do not match the JSON files, or the trend counts sum to 47 instead of 50. The VP spots the error in a board meeting. Fix: add the five verification checks to the orchestrator prompt. The orchestrator catches its own errors before you ship the file.

**Missing the audit footer.** The portfolio summary goes to the board. Without the audit footer, nobody knows which data files or weights were used. If someone questions a score, you cannot trace it back. Fix: include the audit footer text in the orchestrator prompt as a required section.

**Overwriting previous quarter summaries.** If the output file name does not include the quarter and date, running the orchestrator next quarter overwrites this quarter's file. Fix: use the naming convention `portfolio-summary-2026-Q1-2026-04-25.md`. The quarter and date are in the file name.
